## Dette technique / points de vigilance
- Toute future création de compte par SQL direct doit inclure une ligne `auth.identities` + colonnes token en `''` jamais `NULL` (appliqué avec succès une 3ᵉ fois pour le compte fixture Solo).
- Mot de passe temporaire du compte fondateur à changer.
- Réconciliation `transactions_wallet` ↔ `mouvements_financiers` toujours en attente.
- Si un jour un mini-cadran IGA par bénéficiaire est demandé, réutiliser le composant `IgaDial` existant (accepte déjà une prop `value` générique) plutôt qu'en recréer un.
- **Piège Next.js 16 à ne pas reproduire** : un dossier entre parenthèses (`app/(nom)/`) est un *route group* — il n'ajoute jamais de segment à l'URL. Pour une vraie route `/solo`, il faut un dossier `app/solo/` réel (leçon apprise après une collision de build "two parallel pages that resolve to the same path" en ayant initialement construit `app/(solo)/`).
- **Toute Server Action bindée directement sur `<form action={...}>` doit retourner `Promise<void>`**, pas `{error}` — sinon `next build`/`tsc` échoue (React 19/Next 16 exigent ce type précis). Si l'appel se fait de façon impérative depuis un composant client (pas via `<form>`), la fonction PEUT retourner `{error}`, mais il faut alors appeler `router.refresh()` soi-même après succès : `revalidatePath()` seul n'actualise pas une page déjà montée quand l'action n'est pas déclenchée par une soumission de formulaire. Bug réel rencontré et corrigé sur `ConfirmModal.tsx` (la suppression de formation semblait ne rien faire tant que ce `router.refresh()` manquait).
- **Fichiers Storage orphelins** : la suppression d'une formation cascade sur `ressources_formation` (FK) mais PAS sur les objets réels du bucket Storage (système séparé, pas de cascade SQL possible) — les fichiers restent dans `ressources-formations` même après suppression de la ligne. Non bloquant à ce stade (bucket de test), mais à traiter si le volume devient réel (job de nettoyage périodique ou suppression explicite du fichier avant suppression de la formation).
- **Playwright et RLS `hasText`** : un `div` ancêtre "contient" toujours le texte de ses enfants — `.filter({hasText}).first()` ou `.last()` peuvent tous deux sélectionner le mauvais niveau selon la profondeur de l'arbre. Solution appliquée systématiquement : scoper sur une classe CSS propre à la carte/ligne ciblée (`div.py-4`, `div.py-3`) plutôt que sur `div` générique.
- **Suite Playwright et rate-limit Supabase Auth** : `playwright.config.ts` force `workers: 1`. Ne pas paralléliser sans vérifier que le rate-limit GoTrue le supporte (comportement observé : échecs de login en cascade dès 6 workers, aucun rapport avec le code applicatif).
- **Deux systèmes de marketplace coexistent** : `formations` (pédagogique, auto-publication sans modération) et `marketplace_offres` (produit/service, modération Fondateur obligatoire depuis l'Étape 16). Unifiés uniquement en lecture via `vue_marketplace_publique`. Voir `JOURNAL-AUTONOMIE.md` pour la décision complète et pourquoi une fusion n'a pas été tentée sans confirmation d'Angenor.
- **Ne jamais interpoler une entrée utilisateur libre directement dans une chaîne de filtre PostgREST** (`.or(\`...${q}...\`)`) sans la nettoyer d'abord — trouvé et corrigé dans `app/solo/marketplace/page.tsx` (caractères `,().` pouvaient détourner le filtre prévu). RLS reste la protection de fond, mais ce n'est pas une raison de laisser ce genre de trou ouvert.
- **Nouveau motif de bug de permission à surveiller pour tout futur module Compte Solo/Employeur** : le rôle `administrateur` a systématiquement `peut_supprimer=false` par défaut dans les seeds de permissions de l'architecture v5 (voulu pour les structures/employeurs à plusieurs intervenants) — et pour `marketplace_offres`, la policy de delete d'origine (Étape 16) n'avait même aucune clause `organisation_id` du tout. Déjà trouvé et corrigé trois fois (`formations`, `beneficiaires`, `marketplace_offres`) via une policy RLS additionnelle scopée par type d'organisation. Si un futur module ajoute une action de suppression, vérifier ce point AVANT de découvrir le bug en test.
- **`app/page.tsx` (route racine) doit rester supprimé** : c'était un prototype thème clair oublié depuis les tout premiers commits, en collision silencieuse avec `app/(dashboard)/page.tsx` sur `/` — contrairement à la collision `(solo)`/`(dashboard)` déjà rencontrée, Next.js/Turbopack n'a jamais signalé d'erreur de build pour celle-ci, il choisissait l'un des deux fichiers de façon non déterministe selon l'état du serveur de dev. Si un jour un vrai besoin de page à la racine hors du groupe `(dashboard)` apparaît, bien vérifier qu'aucun autre fichier ne résout déjà vers le même chemin.
- **Un dev server Next.js qui tourne depuis des heures peut masquer un vrai bug plutôt qu'un cache périmé** : avant de conclure "c'est juste le cache Turbopack, je redémarre", vérifier s'il n'existe pas un second fichier de route en conflit — le redémarrage seul n'aurait pas suffi ici (le bug persistait après redémarrage complet, la vraie cause était `app/page.tsx`).
- **Deux sessions Claude Code peuvent partager le même serveur de dev (port 3000) et le même projet Supabase distant sans le signaler explicitement.** Détecté cette session via des routes admin (`/marketplace`, `/communication`) apparaissant dans les logs du serveur alors que je ne les visitais pas, puis confirmé par un vrai timeout de connexion Postgres direct (`supabase db query`) — la lenteur ambiante (logins/pages à 10-25s, tests Playwright échouant sur de simples timeouts par défaut de 5s) n'était donc PAS une régression de code mais une contention de ressources partagées. Le redémarrage du serveur ne règle rien dans ce cas (contrairement au cas `app/page.tsx` ci-dessus) puisque le serveur redémarré est de toute façon repartagé aussitôt. Réflexe à appliquer avant de chercher un bug de perf : vérifier les logs serveur pour des requêtes vers des routes qu'on n'a pas soi-même visitées.
